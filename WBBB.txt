White Box Testing

White Box Testing is a software testing technique where the tester has knowledge of the internal code, logic, structure, and flow of the application.

In simple words:

White Box Testing = Testing the inside of the software/code.

The tester looks at how the program works internally, rather than only checking what output it produces.

Simple Example

Suppose we have:

if (age >= 18) {
    System.out.println("Eligible to Vote");
} else {
    System.out.println("Not Eligible");
}

In Black Box Testing, we mainly test:

age = 20 → Eligible
age = 15 → Not Eligible

In White Box Testing, we also examine the code and ask:

Did we execute the if condition?
Did we execute the else condition?
Are both paths tested?
Are all statements executed?
What happens at different logical conditions?
Types of White Box Testing

The major types/techniques are:

1. Statement Coverage
2. Branch Coverage
3. Path Coverage
4. Condition Coverage
5. Decision Coverage
6. Data Flow Testing
7. Control Flow Testing

For students, I recommend teaching the first 5 first, because they are easier to understand.

1. Statement Coverage

Statement Coverage checks whether every executable statement in the code has been executed at least once.

Example
if (age >= 18) {
    System.out.println("Adult");
}

System.out.println("Welcome");

Test:

age = 20

Execution:

if condition → TRUE
     ↓
Print "Adult"
     ↓
Print "Welcome"

Both statements are executed.

So:

Statement Coverage = 100%

Formula

Statement Coverage =

Executed Statements / Total Statements × 100

Easy student explanation

"Did we run every line of code?"

2. Branch Coverage

Branch Coverage checks whether each possible branch/outcome of a decision has been executed.

For example:

if (age >= 18) {
    System.out.println("Adult");
} else {
    System.out.println("Minor");
}

There are two branches:

        age >= 18?
         /      \
      TRUE      FALSE
       ↓          ↓
    Adult       Minor

We need two test cases:

Test Case	Age	Result	Branch
TC01	20	Adult	TRUE
TC02	15	Minor	FALSE

Therefore:

Branch Coverage = 100%

Easy explanation

"Did we test every direction the decision can take?"

3. Path Coverage

Path Coverage checks whether different execution paths through the program have been executed.

Consider:

if (age >= 18) {
    if (hasLicense) {
        System.out.println("Can Drive");
    }
}

Possible paths include:

Path 1:
age >= 18 → FALSE
        ↓
       END
Path 2:
age >= 18 → TRUE
        ↓
hasLicense → TRUE
        ↓
Can Drive
Path 3:
age >= 18 → TRUE
        ↓
hasLicense → FALSE
        ↓
END

So we need test cases covering these different paths.

Easy explanation

"Did we test all possible routes through the code?"

4. Condition Coverage

Condition Coverage checks whether each individual condition evaluates to TRUE and FALSE.

Example:

if (age >= 18 && hasLicense) {
    System.out.println("Can Drive");
}

There are two conditions:

Condition 1 → age >= 18
Condition 2 → hasLicense

We want each condition to become:

TRUE
FALSE

at least once.

Example:

Test	Age	License	Age ≥ 18	License	Result
TC01	20	Yes	TRUE	TRUE	Drive
TC02	20	No	TRUE	FALSE	No Drive
TC03	16	Yes	FALSE	TRUE	No Drive

Now both conditions have been tested as TRUE and FALSE.

Easy explanation

"Did every individual condition get a chance to be TRUE and FALSE?"

5. Decision Coverage

Decision Coverage checks whether the overall decision result becomes both TRUE and FALSE.

Example:

if (age >= 18 && hasLicense) {
    System.out.println("Can Drive");
}

The overall decision is:

age >= 18 AND hasLicense

We need:

TRUE  → Can Drive
FALSE → Cannot Drive

Example:

Age	License	Overall Decision
20	Yes	TRUE
20	No	FALSE

Therefore, both decision outcomes are covered.

6. Data Flow Testing

Data Flow Testing focuses on how variables are declared, assigned, used, and modified throughout the program.

Example:

int marks;

marks = 80;

if (marks >= 40) {
    System.out.println(marks);
}

Here:

Declaration → marks
Assignment  → marks = 80
Usage       → marks >= 40
Usage       → println(marks)

We check whether data is being properly handled throughout its lifecycle.

Easy explanation

"Where is the data created, changed, and used?"

7. Control Flow Testing

Control Flow Testing focuses on the flow of execution within the program.

Example:

       Start
         ↓
    Check Age
      /    \
   TRUE    FALSE
    ↓        ↓
 Adult     Minor
    \        /
      ↓
     End

The tester studies this flow to identify different execution routes.

It is commonly represented using a Control Flow Graph (CFG).

Easy explanation

"How does the program move from one statement/decision to another?"

White Box Testing — Quick Comparison
Technique	Main Question
Statement Coverage	Did we execute every statement?
Branch Coverage	Did we execute every branch?
Path Coverage	Did we test different execution paths?
Condition Coverage	Did every condition become TRUE and FALSE?
Decision Coverage	Did the overall decision become TRUE and FALSE?
Data Flow Testing	How is data created, changed and used?
Control Flow Testing	How does execution flow through the program?

Give them this simple memory trick:

Statement → Line
Branch → Direction
Path → Route
Condition → Individual Condition
Decision → Overall Result
Data Flow → Variable/Data
Control Flow → Program Movement

One-line definition for exams

White Box Testing is a software testing technique in which the internal code, logic, structure, conditions, and execution paths of the 
application are examined and tested.

Important: White Box Testing is generally associated with developers or testers who have access to source code, 
and it is commonly used at the unit and integration testing levels.


Black Box Testing and Its Types
What is Black Box Testing?

Black Box Testing is a software testing technique where the tester tests the functionality of the application without knowing or examining its internal source code or implementation logic.

In simple words:

Black Box Testing = Test the software from the outside without looking inside the code.

The tester focuses on:

What input is given?
What output is expected?
Does the application behave according to the requirements?
Simple Example — Login Page

Suppose we have:

Username: __________
Password: __________

       [ Login ]

A Black Box tester doesn't care how the login functionality is coded internally.

They test:

Test	Username	Password	Expected Result
TC01	valid	valid	Login successful
TC02	valid	invalid	Error message
TC03	invalid	valid	Error message
TC04	blank	blank	Validation message
TC05	valid	blank	Password required

The tester is checking behavior, not source code.

Types of Black Box Testing

Black Box Testing can be divided into different test design techniques.

The most important ones for students are:

Equivalence Partitioning (ECP)
Boundary Value Analysis (BVA)
Decision Table Testing
State Transition Testing
Use Case Testing
Error Guessing

Let's understand each with simple examples.

1. Equivalence Partitioning — ECP
Idea:

Instead of testing every possible input, we divide inputs into groups called equivalence classes.

We assume that values within the same group should behave similarly.

Example

Suppose an application accepts age from 18 to 60.

We can divide the inputs into:

Partition	Age	Valid/Invalid
Class 1	Below 18	❌ Invalid
Class 2	18–60	✅ Valid
Class 3	Above 60	❌ Invalid

Instead of testing:

1, 2, 3, 4, 5...17

we can select representative values:

10 → Invalid
30 → Valid
70 → Invalid
Easy student explanation

ECP = Divide a large group into smaller groups and test representative values.

2. Boundary Value Analysis — BVA

BVA focuses on the boundaries/edges of valid and invalid ranges.

Why?

Because defects frequently occur around boundaries.

Example

Age allowed:

18 ───────────── 60

We should test:

17 → Invalid
18 → Valid
19 → Valid

59 → Valid
60 → Valid
61 → Invalid

So:

Input	Expected
17	❌ Invalid
18	✅ Valid
19	✅ Valid
59	✅ Valid
60	✅ Valid
61	❌ Invalid
Easy student explanation

BVA = Test the edges.

Memory Trick

ECP → Groups

BVA → Boundaries

3. Decision Table Testing

Decision Table Testing is useful when the application's behavior depends on multiple conditions or business rules.

Example — Loan Approval

Suppose a bank approves a loan when:

Customer has a good credit score
Customer has sufficient income
Condition	Rule 1	Rule 2	Rule 3	Rule 4
Good Credit?	Yes	Yes	No	No
Sufficient Income?	Yes	No	Yes	No
Decision	Approve	Reject	Reject	Reject

This helps us test different combinations of conditions.

Easy student explanation

Decision Table = Test combinations of conditions and their resulting actions.

4. State Transition Testing

State Transition Testing is used when the system's behavior changes depending on its current state.

Example — ATM Card

Imagine an ATM card has these states:

Active
   ↓
Wrong PIN
   ↓
Wrong PIN
   ↓
Wrong PIN
   ↓
Blocked

We can test:

Current State	Action	Next State
Active	Correct PIN	Active
Active	Wrong PIN	Wrong PIN Count = 1
Wrong PIN 1	Wrong PIN	Wrong PIN Count = 2
Wrong PIN 2	Wrong PIN	Blocked

Another common example is an e-commerce order:

Placed
  ↓
Confirmed
  ↓
Shipped
  ↓
Delivered

The system behaves differently depending on the current state.

Easy student explanation

State Transition = Test how the application moves from one state to another.

5. Use Case Testing

Use Case Testing focuses on testing the system based on real-world user scenarios.

For example, an e-commerce application may have:

Login
   ↓
Search Product
   ↓
Add to Cart
   ↓
Checkout
   ↓
Make Payment
   ↓
Order Confirmed

We can create test cases around this complete user journey.

Example

Use Case: Purchase a product

Login
Search product
Select product
Add to cart
Checkout
Enter address
Make payment
Verify order confirmation

We can also test alternate scenarios:

Payment Successful → Order Confirmed

Payment Failed → Payment Error

Product Out of Stock → Cannot Purchase
Easy student explanation

Use Case Testing = Test the application through real user scenarios.

6. Error Guessing

Error Guessing is based on the tester's experience, intuition, and knowledge of common mistakes.

The tester tries inputs or actions that are likely to cause defects.

Example — Login

A tester may try:

Username = blank
Password = blank

Then:

Username = valid
Password = blank

Then:

Username = blank
Password = valid

They might also try:

Very long username
Very long password
Special characters
Spaces
Copy-paste values
Multiple rapid clicks on Login
Browser Back button
Refresh during login

These tests aren't necessarily derived from a formal mathematical technique; they come from tester experience and likely failure points.

Easy student explanation

Error Guessing = "I know where bugs usually hide, so I'll try those situations."

Quick Comparison of Black Box Techniques
Technique	Focus	Simple Question
ECP	Input groups	"Can I divide inputs into groups?"
BVA	Boundaries	"What happens at the edges?"
Decision Table	Conditions & combinations	"What happens for each combination?"
State Transition	States & transitions	"What happens when the state changes?"
Use Case Testing	User scenarios	"Can the user complete the entire activity?"
Error Guessing	Common mistakes	"Where do I think bugs might be?"
ECP vs BVA — Very Important

Students often confuse these two.

Suppose:

Password length must be 8–16 characters.

ECP

Create groups:

< 8       → Invalid
8–16      → Valid
> 16      → Invalid

Representative values:

5   → Invalid
10  → Valid
20  → Invalid
BVA

Test around the boundaries:

7   → Invalid
8   → Valid
9   → Valid

15  → Valid
16  → Valid
17  → Invalid
Remember:

ECP = Test the groups
BVA = Test the edges of the groups

Black Box vs White Box
Black Box	White Box
Doesn't require knowledge of source code	Requires knowledge of internal code/logic
Tests external behavior	Tests internal logic/structure
Focuses on input and output	Focuses on code paths and statements
Commonly performed by testers	Often performed by developers/testers with code knowledge
ECP, BVA, Decision Table, State Transition	Statement, Branch, Path, Condition Coverage
One-line memory trick for students

🔲 Black Box: "I don't care how you built it; I'll check whether it works."
⬜ White Box: "I know how you built it; I'll check whether the internal logic works correctly."

28. One Important Teaching Point

Don't teach students:

❌ "Jira is an Agile tool."

Instead teach:
